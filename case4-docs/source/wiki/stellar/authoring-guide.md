使用指南应该帮助读者完成一件事。开始写之前，先补全这句话：“读完这页，读者可以……”如果答案包含好几个互不相关的动作，就把它们拆成不同页面，再通过导航连接。

## 先交代任务和前置条件

以“给项目新增一篇文档”为例，读者需要知道文件放在哪里、哪些字段必须填写，以及完成后从哪里打开页面。这些信息应该出现在步骤之前，避免读到一半才发现缺少准备。

{% note color:cyan 本页使用场景 下面的路径对应 docs 示例。下载为独立站点后，从站点根目录操作；在 examples 仓库中，则从 case4-docs 目录查看这些文件。 %}

文档正文保存在 `source/wiki/stellar/`。新建页面时，可以从下面的元数据开始，其中标题与地址按实际内容替换：

```yaml
---
title: 我的第一篇指南
collection:
  profile: wiki
  id: stellar
permalink: /first-guide/
---
```

## 按读者的问题安排正文

{% tabs %}
<!-- tab 操作指南 -->
先说明要完成的任务，再列前置条件，然后按顺序给出操作。每一步尽量只要求一个动作，命令之后说明应当出现的结果。

适合“创建一篇页面”“调整菜单入口”这类有明确终点的任务。
<!-- tab 配置参考 -->
先说明字段控制什么，再写取值、默认行为与一个完整示例。多个字段互相依赖时，将它们放在同一个片段里解释。

适合读者已经知道目标，只需要查找准确写法的场景。
<!-- tab 问题排查 -->
用读者能观察到的现象作为标题。先帮助确认问题，再说明可能原因，最后给出最小的检查步骤。

例如“文档已经生成，但侧栏没有入口”，比“导航系统说明”更容易对应眼前的问题。
{% endtabs %}

## 给步骤一个结束标志

写完页面后，还需要在 `source/_data/wiki/stellar.yml` 的 `navigation.tree` 中加入它的完整路径。生成站点后，从侧栏点击入口，确认标题、正文和当前页状态都对应这篇页面。

好的结束标志应该能直接观察，例如“侧栏出现新标题，点击后进入 `/first-guide/`”。“配置完成”太笼统，无法帮助读者判断漏掉了哪一步。

## 让扩展说明保持可选

{% folding color:cyan 发布前可以删掉哪些内容？ %}
删掉与本页任务无关的历史背景、重复出现的命令，以及只有维护者才需要知道的内部细节。必要的限制保留在相关步骤旁边，进阶材料则链接到独立页面。

重新读一遍开头与结尾：读者开始时的问题，是否已经在正文里得到回答？
{% endfolding %}
