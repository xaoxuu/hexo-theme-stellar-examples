给博客调整导航，看起来只是改几个名称。真正动手时才发现，我还需要回答哪些内容应该放在一起、哪些入口没人使用，以及读者进入文章后怎样继续阅读。

<!-- more -->

## 先记录问题，再记录改动

以前的维护日志经常只有一句“优化导航”。几周后再看，既不知道当时哪里不好用，也无法判断这次调整有没有帮助。现在我会先写下一个具体场景：从首页寻找上个月的阅读笔记，需要连续打开三个不同入口。

这个场景为调整提供了边界。目标不是让菜单看起来更丰富，而是让同类内容有一个稳定的位置。下面是一轮小改动的示例记录。

{% timeline %}
<!-- node 第一天：列出现有入口 -->
把顶部菜单、侧栏和页脚里的链接写到同一张纸上。发现“随笔”和“生活”包含几乎相同的文章，却让读者以为是两组内容。
<!-- node 第二天：缩小调整范围 -->
保留“生活”作为分类，把“随笔”留给表达形式的标签。先检查五篇旧文章，不一次性重写整个分类体系。
<!-- node 第三天：重新走一遍路径 -->
从首页进入分类，找到目标文章，再通过标签打开相关内容。记录仍然让人迟疑的名称，留给下一轮调整。
{% endtimeline %}

## 完成状态要对应可见的结果

给任务打勾时，我尽量使用能直接检查的描述。“体验更好”没有明确的完成时刻，“五篇旧文章已经能从生活分类进入”则可以马上确认。

{% checkbox checked:true color:green 首页、分类页和文章页之间能够相互到达。 %}
{% checkbox checked:false color:yellow 继续观察是否还会把分类与标签的用途弄混。 %}

## 为下一次维护留下线索

日志最后保留两句话：这次决定了什么，还有什么没有决定。例如，暂时保留旧文章地址，后续再考虑是否合并内容。这样下一次整理时，就不会把尚未完成的讨论误认为一个已经确认的方案。

小项目不需要写成正式报告。只要未来的自己能看懂“为什么这样改”，这篇日志就比一串笼统的完成记录更有用。
